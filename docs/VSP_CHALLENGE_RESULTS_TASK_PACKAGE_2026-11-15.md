## دلائل المصدر وحدودها

- `match_result_modal.dart` يحتفظ بثلاثة اختيارات من منظور فريق المرسل، ويحوّلها إلى `homeWin/awayWin/draw`. لا نضيف أهدافًا أو إحصاءات فردية.
- `20261003193000_challenge_mutual_result_agreement_and_points.sql` موجود بالنص نفسه في الفرعين. دالة `submit_challenge_result_atomic` تقفل صف الحجز وتفحص نهاية الموعد والكابتن، لكنها تستعمل حقلي اختيار معلّق واحد ومرسل واحد؛ عند التعارض تستبدل الاختيار السابق. وجودها لا يثبت حفظ اختيارين مستقلين أو التدقيق الكامل أو كل حالات الأهلية.
- `challenge_result_actions.dart` في فرع التطوير يعرض «الفريق المنافس سجل» مع قيمة الاختيار قبل إرسال الرد؛ إخفاء الواجهة وحده لن يفي بـ RESULT-03 إذا ظل الاختيار ظاهرًا عبر API أو Realtime.
- ملف تعطيل `auto_reconcile_single_entry_results` موجود في الفرعين، لكن ملفًا قديمًا آخر يعرّف `auto_approve_challenge_matches_24h` ويجدول استدعاءه. تعطيل اسم واحد لا يثبت إزالة كل المسارات. لا نفترض أي وظيفة أو جدول زمني منشور حاليًا دون فحص لاحق مصرح به.
- `calculate_elo_on_match_completion` في المصدر يضيف نقاط المنافسة 3/1/0 ويستعمل `elo_processed` لمنع المعالجة العادية المتكررة. العلم وحده لا يثبت سلامة عكس التأثير والاستعادة أو إعادة البناء. توثيق المعادلة المقبول 37.01 محفوظ دون تغيير حالته.
- `20260925290000_harden_owner_no_show_atomic.sql` يغير `status/is_paid/payment_status`، ويعتبر العربون تعويضًا، ويخصم 10 من `fair_play_score`. لذلك لا يصلح نسخه أو ربطه مباشرة ببلاغ عدم اللعب المحايد ماليًا. توجد ترقيعات أمن لاحقة؛ المطلوب لاحقًا مراجعة التعريف المنشور واعتمادياته كاملة.

هذه نتائج قراءة المصدر فقط. لم نستعلم عن حسابات أو بيانات مباريات في Supabase ولم ننفذ SQL أو Cron أو RPC أو نشرًا أو اختبارًا وظيفيًا جديدًا. وجود كود أو CI سابق لا يغلق هذه المتطلبات.
