## 01.02 — Every numbered UXLP rule has source-level implementation review
The [authoritative audit](UXLP_44_RULE_AUDIT.md) includes exactly 44 ordered rules, all with substantial implementation/risk evidence. For 39 rules it records **source reviewed—runtime pending**, and for 25, 31, 38, 39, 41 it documents **needs product decision**. The [screen mapping](VSP_UXLP_44_RULE_SCREEN_MAP_01_01_2026-11-19.md) binds each rule to representative player and owner/auth source surfaces with 88 grounded references across 30 distinct files. Reviews cover hierarchy/typography and tokens (1–11), decisions and financial context (12–24), action guards and accessibility (25–37), lifecycle/roles/source authority (38–44). Important unresolved server decisions include result kickoff enforcement, active-league caller authorization and captain contact privacy; historical findings must be revalidated on staging. This is a **review outcome**, not a claim that the rules have been fixed, all 338 screens tested, or approved at runtime; the remaining 01.04–01.06 are open.

## 12.04 — Private editing fields never follow a switched session on the client
`EditProfileScreen` now requires the authenticated Supabase ID to match both the hydrated profile UID **and** the ID at which the edit form opened. When a different account signs in or a stale profile persists, the screen immediately displays neutral localized information rather than the previous user's name, phone, selected position or avatar. It refuses writes and ignores late profile/photo callbacks on session mismatch; the form must be reopened for the newly authenticated user. Dedicated tests cover Arabic/English, initial mismatch, identity switch in-flight, and hydrated new account in the stale form. This does **not** replace backend profile ownership policies; those remain under 78/79 and staging tests. Captain phone visibility in public team pages needs independent consent/product review.

## 13.06 — Editing football position preferences
Player can change their preferred football position from GK to FW; the actual selected position is in the sanitized update payload and no role/UID field is sent. The selection is disabled while async saving, preventing the UI from silently diverging from the submitted value. Tests verify both locales, invalid code failure before writes, owner/player isolation, stale-account handling, and retry after a mocked failed save. No invented secondary position, no new schema/paid entitlements, and no claim of live Supabase write verification. 13.02–13.04 remain open.
