# VSP — دفعة 05: حواجز أدوار الحسابات وفحوص SQL الآلية
التاريخ: 2026-11-11 (القاهرة). المصدر السابق 3da3c5e، فرع uxlp-44-implementation. موافقة المالك الأخيرة شاملة للتنفيذ اللازم؛ لا تتطلب إعادة سؤال عند كل خطوة. لا تغيير أسعار/نموذج الاشتراك أو دمج main.

## الإصلاح الفعلي
P0: الكتابة المباشرة في users يمكن أن تختار دور admin عند إنشاء ملف، وامتياز المستخدم الإداري في سياسة users_admin_manage_all مع تجاوز الحماية القديم يسمح بتعديل دوره إلى مؤسس مباشرة، متجاوزاً طلب إدارة الأدوار المقيد.
- إضافة guard_client_profile_role_mutations كـSECURITY INVOKER: العملاء anon/authenticated ينشئون player/owner فقط، ولا يغيرون حقل role مباشرة حتى لو كان ملفهم إدارياً.
- الطلبات المخولة SECURITY DEFINER تحتفظ بعملها ودورها في التحقق؛ set_user_role_on_signup يعمل. لا ثقة في user_metadata ولا علم vsp.system_override لإجازة تغيير الدور المباشر.
- مسارات legacy لإنشاء player/owner وتعديل الإدارة للتحذيرات تبقى عاملة؛ لا سحب جديد لمنح INSERT/DELETE على الإنتاج بهذه migration. الحماية الإضافية لا تعالج وحدها كل حقول الاشتراك والبيانات المالية أو الحذف المباشر.
- SQL الجديدة اختبرت محلياً وفي معاملة ROLLBACK على staging، ثم نشرت على staging وأعيد اختبارها بنجاح. بعد نجاح PostgreSQL الأصلي ومراجعة استعمال لوحة الإدارة، نشرت الحماية الإضافية على الإنتاج بموافقة المالك الشاملة. لا صفوف عملاء حقيقيين قرئت أو عدلت في النشر. المستودع vsp-admin-panel يستخدم admin_set_admin_role_atomic للترقية، والحذف عبر delete_user_permanently؛ الحماية لا تعطل هذه الطلبات.

## الفحص الآلي الجديد
- workflow Account SQL security contracts: قاعدة PostgreSQL 17.6 مؤقتة، بلا مفاتيح Supabase أو بيانات إنتاج، عند تغيير SQL/الاختبارات وأداة التشغيل ويدوياً.
- 5 مجموعات SQL: إلغاء التسجيل/المحادثات، حماية الحقول الحساسة، إنشاء الملف، عزل قراءة/تعديل ملفات اللاعب والمالك وصلاحيات الإدارة، وحماية الدور مع الحفاظ على طرق الإنشاء القديمة.
- 5 fault controls: تعطيل RLS، منح anon حق provision، حذف فحص اكتمال التسجيل، حذف فحص عضوية المحادثة، وإزالة حماية الدور. كل منها يجب أن يسبب فشل الاختبار للسبب الأمني المحدد، لا لخطأ إنشاء جدول.
- رفض إعادة تجهيز قاعدة سبق إنشاؤها والتحقق من خلو جداول الحسابات من بقايا الاختبارات.
- runner يرفض أي هدف غير loopback أو اسم قاعدة غير vsp_security_contracts، ويزيل PGHOSTADDR/PGSERVICE/PGSERVICEFILE/PGOPTIONS؛ 9 اختبارات Python نجحت محلياً لحواجزه.
- manifest يحدد ما يحمل وينفذ بالضبط؛ لا تشغيل تلقائي لكل migrations المتعارضة.

## مصدر fixture وحدوده
نسخة metadata من staging: 25 جدولاً و518 تعريف عمود و8 تعريفات دوال اعتماد و5 سياسات users. لا صفوف عملاء أو مفاتيح. المصدر الخام في account_security_metadata_2026-11-11.json، والـDDL القابل للتنفيذ في account_security_dependencies.sql.
- تعاريف الأنواع/default/NOT NULL من المصدر؛ PK(id) وFK users→auth فقط ضمن fixture، لا كامل القيود أو تريجرات المشروع.
- helpers auth.uid/jwt/role وتعريفات الاعتماد من staging. الأجسام الجديدة تقرأ من ملفات migration نفسها.
- JWT claims تحقن لاختبار تفويض SQL، وليست إثبات جلسة GoTrue أو OAuth حقيقية.
- هذا اختبار عقود الحسابات وليس إعادة بناء كاملة لقاعدة Supabase أو معالجة تصادمات migrations.
- لا يثبت عزل كل جدول/التخزين/المدفوعات أو كل الدوال المعروضة. مهام عزل الرحلات وتغطية الباقي تبقى مفتوحة.
