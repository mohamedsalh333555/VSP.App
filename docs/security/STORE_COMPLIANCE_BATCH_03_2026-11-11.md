- اختبار الحالة القديمة حتمي: إكمال الخادم أولاً ثم وصول الإلغاء. محاولة مراقبة جلستين لم تثبت تداخل التنفيذ؛ لا نجاح لتزامن حقيقي محسوب. الحساب الاصطناعي الوحيد المحفوظ مؤقتاً للتجربة حذف بمسار حذف الحساب ثم تحقق غيابه من auth/public. القفل موجود في مسار الخادم ولا يدعى قياس سباق كامل.

## استكمال نفس الدفعة: إصلاحان في بيئة الاختبار
- اكتشف أن جسمي trg_fn_protect_user_sensitive_fields وvsp_guard_sensitive_owner_profile_changes موجودان، لكن المشغّلين المرتبطين بتحديث users مفقودان على staging. فحص الإنتاج اقتصر على تعريف المشغلات والدوال؛ الارتباطان موجودان فيه ولم يعدلا.
- إثبات قبل الإصلاح، بمعاملة ROLLBACK وحساب اصطناعي وأعلام خادم معطلة: تعديل الدور إلى admin والخطة إلى pro والحساب البنكي نجح بصفة authenticated. لا بيانات حقيقية قرئت أو غُيرت.
- migration ثانية restore_user_security_trigger_bindings أعادت الارتباطين فقط، بلا تغيير جسمي الدالتين أو قواعد التسعير. النشر على staging نجح.
- بعد الإصلاح: 11 تحققاً نجحت (8 تعديلات حساسة مرفوضة، تعديل اسم مسموح، تعديل بنكي بعد ادعاء password حديث مسموح، تحقق الحالة النهائية). هذا اختبار للادعاءات داخل قاعدة البيانات، وليس تسجيل دخول فعلي بكلمة مرور.
- أعيدت حالات إلغاء التسجيل/المحادثات الـ17 بنجاح بعد الإصلاح. كل هذه البيانات ألغيت بـROLLBACK.
- فشل اختبار أولي بعد استعادة الحماية لأن مزامنة بريد الحساب الاصطناعي تركت علم vsp.system_override=true داخل المعاملة. صُحح الاختبار لمسح العلم قبل تمثيل طلب مستخدم مستقل. لم يعتبر نجاحاً للحماية، وسجل BUG-029.
- المستشار قبل RPC الجديدة: 4 تحذيرات extensions، 198 دالة SECURITY DEFINER مسموحة للمسجلين، 1 حماية كلمات مسربة. بعد RPC: 199 دالة؛ التحذير الإضافي متوقع لواجهة RPC المقصودة، موثق مع تحقق الملكية وقفل الحالة ورفض anon. لا ادعاء أن المستشار خال من التحذيرات، ولا معالجة إعداد كلمات المرور المؤجل.
- إنشاء اسمي ملفي migration بواسطة CLI. سجل staging أعطى النسخة 20261111012954 للأولى؛ اسمها يطابق الدفعة لكن timestamp المنفذ يختلف عن ملف CLI 20261111012758. أجسام CREATE OR REPLACE قابلة لإعادة التطبيق؛ يلزم تسوية سجل الترحيل قبل إصدار نهائي، بلا كتابة مباشرة في جدول تاريخ الترحيل.
