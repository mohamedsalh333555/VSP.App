# VSP Work Protocol — القواعد الدائمة

## اللغة
- تكلّم بالمصري دايماً.

## القاعدة الذهبية
- **ما تعدّلش سطر كود واحد إلا بعد موافقة المستخدم.**

## بروتوكول الـ 7 مراحل

### 1. 🔍 استكشاف (بدون موافقة) — **لازم تشمل الاتنين:**

#### 1A. 📱 Flutter Client
- اقرأ الكود المتعلق بالمشكلة وتتبع الـ flow كامل.
- افحص كل `onPressed` / `onTap` / async handler ومدى تعامله مع الـ errors.
- افحص الـ side effects على الشاشات المجاورة.

#### 1B. 🗄️ Supabase Backend — **إجباري دايماً**
- افحص ملفات الـ SQL في `supabase/migrations/` المتعلقة بالمشكلة.
- تحقق من وجود Triggers تحمي أو تمنع العملية (BEFORE INSERT / UPDATE / DELETE).
- افحص الـ RLS Policies على الجداول المتعلقة — مين يقدر يعمل إيه.
- افحص الـ Functions/RPC المستدعاة من الكود — هل موجودة وهل منطقها صح.
- افحص الـ Foreign Keys وقواعد الـ ON DELETE (CASCADE / SET NULL / RESTRICT).
- **إذا كانت هناك بيانات أو كويريز أو صلاحيات غير موجودة بملفات المشروع، اطلبها فوراً من المستخدم في الشات قبل أي افتراض.**
- **لا تكتب التقرير غير بعد ما تفحص الاتنين (Client + Backend) معاً.**

### 2. 🩺 تشخيص → رجّع تقرير مُنظّم
- 📍 المكان (ملف + سطر)
- 🔴 المشكلة (وصف دقيق)
- 🌳 السبب الجذري (ليه المشكلة حصلت أصلاً — مش بس العَرَض)
- ⚠️ الخطورة (🔴 حرج / 🟠 عالي / 🟡 متوسط / 🟢 تحسين)
- 🔗 التأثير
- 💣 خريطة الضرر (كل ملف و function هيتأثر بالتعديل)
- 🏆 **هل ده أفضل حل على الإطلاق؟** (مقارنة الحل مع البدائل الممكنة والتأكد إنه الأقوى والأنظف معمارياً وأمنياً قبل طرحه)
- 💡 الحل المقترح (بالكلام بدون كود)
- 🔙 خطة الرجوع (لو التعديل كسر حاجة — إزاي نتراجع)
- 📊 قبل/بعد

### 3. ⛔ استنى الموافقة
- "نفّذ" → المرحلة 4
- "وضّح أكتر" → شرح إضافي → استنى تاني
- "لأ" / "غيّر" → عدّل الخطة → استنى تاني

### 4. ⚡ تنفيذ (بعد الموافقة بس)
- أقل تغيير ممكن (Minimal Change).
- ما تلمسش حاجة مالهاش علاقة.
- حافظ على كل الكومنتات الموجودة.

### 5. 🛡️ فحص ذاتي
- Regression check — التعديل ما كسرش حاجة تانية.
- Edge cases — null, empty, timeout, concurrent.
- Consistency — الأسلوب متوافق مع باقي الكود.
- 📉 الأداء: اتأكد إن التعديل مش هيأثر على سرعة أو استهلاك الذاكرة.
- 📱 تجربة المستخدم: اتأكد إن التغيير منطقي ومفهوم من وجهة نظر اليوزر.

### 6. 📋 تسليم تقرير التنفيذ
- ✅ اللي اتعمل
- 📁 الملفات اللي اتعدلت (مع لينكات)
- ⚠️ انتبه لـ (أي ملاحظات)
- 🧪 نتيجة الاختبار

### 7. 🔄 مراجعة نهائية
- ملاحظات → نرجع نعدّل
- تمام → المهمة اللي بعدها

## ⚙️ قواعد عامة
- **🗣️ اللغة** — مصري طول الوقت.
- **🎯 أقل تغيير** — ما تعملش refactor أو تحسينات غير مطلوبة.
- **📍 الدقة** — حدد الملف والسطر بالظبط دايماً.
- **🔒 الأمان أولاً** — أي تعديل RLS/SQL/Auth → تحذير 🔴 قبل التنفيذ.
- **🧪 اختبار** — شغّل `flutter analyze` + الاختبارات المتعلقة بالتعديل (مش بس static analysis)..
- **🔄 تحديث فوري للمحاكي (إجباري تلقائياً)** — بعد أي تعديل كود واجتياز الفحص، لازم تحدث التطبيق فوراً على المحاكي تلقائياً (Hot-Reload / Run) عشان المستخدم يشوف التعديل مباشرة قدامه بدون ما يحتاج يطلب.
- **❓ ممنوع الفرضيات نهائياً (اسأل دايماً وكثيراً)** — لا تعمل بالفرضيات بل اسألني دائماً وكثيراً لتفادي الأخطاء، وممنوع حذف أي ميزة أو عنصر UI أو منطق برمجي دون الرجوع لي وذكر سبب مقنع وأخذ موافقتي الصريحة.
